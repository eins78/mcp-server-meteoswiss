# MeteoSwiss MCP Server v2.3.0-rc.1 — LLM UX Review

**Date**: 2026-04-08  
**Reviewer**: Claude Opus 4.6  
**Perspective**: LLM consumer evaluating tool usability for end-user conversations

---

## Overall Grade: C+

The server gets the basics right — station discovery, current weather, and forecasts work well for happy paths. The search/fetch combo is genuinely excellent. But the pollen tool is broken, location resolution is dangerously unreliable, and several inconsistencies make the server harder for an LLM to use correctly than it needs to be.

---

## 1. Tool Descriptions

### meteoswissCurrentWeather — B+
**Good**: Clear about what it accepts (names, abbreviations, addresses, coordinates). Mentions "updates every 10 minutes" which helps an LLM set user expectations.

**Issues**:
- Says "Returns temperature, precipitation, wind, humidity, pressure, sunshine, **and more**" — the "and more" is vague. It actually returns dew_point and radiation as well. List them.
- Does not mention that OBS stations exist or that visual observations are (supposed to be) available. If/when this is fixed, the description should explain what makes OBS stations special.
- Does not warn that station name resolution is fuzzy and may return surprising results (e.g., "Zurich" → Kloten airport, not city center).
- Claims "~160 Swiss automatic weather stations" — actual count is 158. Minor.

### meteoswissLocalForecast — B
**Good**: Clear examples of all three input formats. Coverage info ("~6000 Swiss locations") is useful. "Updated hourly" sets expectations.

**Issues**:
- Does not mention that station abbreviations get resolved to postal codes, not to the actual station location. The coordinates may differ.
- Does not warn about the weak location resolver — invalid inputs produce wrong data, not errors.
- "Forecast horizon: up to 9 days" is accurate.

### meteoswissPollenData — C-
**Good**: Mentions "~15 stations" (actual: 16, close). "Useful for allergy sufferers" signals intent.

**Issues**:
- Says "Shows pollen levels by type (birch, grass, etc.)" — but the actual response does NOT show pollen types. The species are unnamed.
- An LLM reading this description would expect to find "birch: 875 particles/m³" in the response. Instead it gets 14 undifferentiated numbers. The description is misleading.
- Does not mention the 7 monitored species by name.
- Does not explain the two measurement windows (6-6 UTC vs 0-0 UTC).

### meteoswissStations — A-
**Good**: Concise and accurate. Filter options well-described.

**Issues**:
- Does not mention that the network includes Liechtenstein (Vaduz).
- Default limit (20) is not mentioned in the description — only in the schema default.

### search — A-
**Good**: Languages listed clearly. Pagination warning about duplicates is honest and helpful. Warning about `date-asc` degrading relevance is excellent LLM guidance.

**Issues**:
- "Defaults to 'content' to exclude application pages" — what are "application pages"? An LLM might not know to use `contentType: "content"` vs omitting it.

### fetch — A
**Good**: Clear instruction to "Use the search tool first". Example URL is helpful. Both format options described.

**Issues**:
- None significant. This is the best-documented tool in the server.

## 2. Parameter Descriptions

### Strengths
- Coordinate validation bounds (45.5-48 lat, 5.9-10.6 lon) are in the schema — prevents out-of-range calls.
- `days` has clear min/max (1-9) with a sensible default (5).
- `limit` has clear bounds (1-200) with sensible default (20).

### Issues
- **`station` vs `location`**: `meteoswissCurrentWeather` uses `station` while `meteoswissLocalForecast` uses `location`. An LLM must remember which is which. Both accept station abbreviations, but `location` also accepts postal codes. The naming doesn't convey this distinction.
- **`station` in pollen**: Accepts station names but uses different abbreviation scheme (PZH vs SMA for Zürich). An LLM that learned "SMA" from stations/weather will try it for pollen and get an error. The error message is excellent, but it would be better if the pollen tool resolved "SMA" or "Zurich" to the nearest pollen station automatically.
- **`id` in fetch**: Named `id` but described as a URL. Should be named `url`.

---

## 3. Response Format

### What works well
- **Station data structure** is consistent: name, abbreviation, elevation, coordinates, canton. Present in both stations and currentWeather.
- **Measurement structure** with explicit `value` and `unit` per field is excellent for LLM consumption. An LLM can reliably say "21.4°C" by reading `{value: 21.4, unit: "°C"}`.
- **Forecast structure** is clean: date, temp min/max, precipitation, weather description, icon URL.
- **Coordinate lookup adds `distance_km`** — an LLM can say "nearest station is X, 0.4 km away".

### What needs fixing

#### Timestamp chaos (3 formats)
| Tool | Format | Example |
|------|--------|---------|
| currentWeather | Compact non-standard | `"202604081530"` |
| localForecast | ISO 8601 ✅ | `"2026-04-08T04:00:35.659886Z"` |
| pollenData | European DD.MM.YYYY | `"07.04.2026 00:00"` |

**Impact**: An LLM must parse three different date formats. The currentWeather format `202604081530` is particularly hostile — no separators, no timezone indicator. An LLM might misparse it as a number.

**Fix**: Use ISO 8601 everywhere. `"2026-04-08T15:30:00+02:00"` for currentWeather.

#### Pollen response is LLM-hostile
The pollen response is the worst data structure in the server. Given this response for one station:

```json
[
  {"type": "concentration pollinique journalière moyenne 6 UTC...", "value": 0},
  {"type": "concentration pollinique journalière moyenne 6 UTC...", "value": 875},
  {"type": "concentration pollinique journalière moyenne 6 UTC...", "value": 0},
  ...
]
```

An LLM cannot:
1. Know that value 875 is Birch
2. Know that value 0 (first) is Alder
3. Distinguish this from the second set of 7 values for the 0-0 UTC window
4. Give useful allergy advice

**What it should look like:**
```json
{
  "pollen": [
    {"species": "Alder", "value": 0, "level": "none"},
    {"species": "Birch", "value": 875, "level": "high"},
    {"species": "Hazel", "value": 0, "level": "none"},
    {"species": "Beech", "value": 31, "level": "low"},
    {"species": "Ash", "value": 206, "level": "moderate"},
    {"species": "Oak", "value": 11, "level": "low"},
    {"species": "Grasses", "value": 0, "level": "none"}
  ]
}
```

Adding a qualitative `level` ("none"/"low"/"moderate"/"high"/"very high") would be particularly valuable — MeteoSwiss publishes these thresholds and they're what allergy sufferers actually care about.

#### `description` and `lead` duplication in search
Search results contain both `description` and `lead`, which are identical in most cases. This wastes LLM context tokens. Either deduplicate or only include `description`.

#### `contentType` in search results is internal
Results show `contentType: "mchweb:pages/detail-page"` — an internal CMS identifier. An LLM doesn't know what `mchweb:pages/detail-page` means. Map to the user-facing types: "content", "press-release", "blog-article", "publication".

## 4. Error Messages

### Hall of Fame (excellent errors)
- **Pollen invalid station**: `'No pollen station found for "NOTASTATION". Available: PBE (Bern), PBS (Basel), ...'` — Lists all 16 stations. Perfect for LLM self-correction.
- **Fetch non-MeteoSwiss URL**: `'Invalid domain: www.google.com. Only MeteoSwiss domains are allowed.'` — Clear scope boundary.
- **Fetch not found**: `'Content not found... Use the search tool to discover valid page URLs.'` — Suggests corrective action.
- **CurrentWeather no params**: `'Either "station" or "coordinates" must be provided'` — Clear.
- **CurrentWeather out-of-range**: Zod validation with exact path and constraint message.

### Hall of Shame (missing/bad errors)
- **CurrentWeather "NOTASTATION"**: Returns Chasseral data instead of error. An LLM will serve the user wrong weather for the wrong place with complete confidence.
- **LocalForecast "99999"**: Returns Bilten data instead of error.
- **LocalForecast "Paris"**: Returns Bettlach data instead of error.
- **LocalForecast "1200" (Geneva)**: Returns Cousset data — a valid Swiss postal code resolving to the wrong city. The most dangerous case.
- **Stations canton "XX"**: Returns empty results with no indication that the canton is invalid. Should say `"Invalid canton 'XX'. Valid cantons: ZH, BE, ..."`.

**Pattern**: The pollen tool and fetch tool have excellent error handling. The weather and forecast tools have dangerous silent fallbacks. The fix should be: if the resolver cannot find a confident match, return an error with suggestions rather than a low-confidence match.

## 5. Missing Features

### High priority
1. **Pollen species names and severity levels** — The tool is unusable without them.
2. **Location resolver confidence threshold** — Return errors for low-confidence matches instead of wrong data.
3. **OBS visual observations** — Cloud cover, visibility, and present weather are valuable for richer weather descriptions.
4. **meteoswissClimateData** — The NBCN homogeneous climate series would make the server useful for climate research questions.

### Medium priority
5. **Wind direction as compass** — Currently returns `57°`. Add a `compass` field: `"ENE"`. LLMs (and users) think in compass directions, not degrees.
6. **Weather description for currentWeather** — Forecast has `"weather": "sunny"` but current weather has no equivalent. An LLM must synthesize "sunny" from radiation=438 W/m² and sunshine=10 min. Add a `conditions` field.
7. **Precipitation probability** — Forecast has total precipitation but not probability. "20% chance of 5mm rain" is more useful than "5mm".
8. **Forecast hourly breakdown** — Daily min/max is coarse. Hourly data exists in the OGD API.

### Low priority
9. **Station type indicator** — Flag whether a station is SMN (automatic), OBS (manned), SMN-precip (rain-only), or pollen.
10. **Data freshness indicator** — currentWeather shows a timestamp but doesn't say if data is stale. If last update was >30 min ago, flag it.
11. **Search result count optimization** — Return `totalResults` and first N results. Currently all results count against context tokens.

## 6. Consistency

### Naming inconsistencies
| Concept | Tool A | Tool B |
|---------|--------|--------|
| Location input | `station` (currentWeather) | `location` (localForecast) |
| Station ID | `SMA` (weather stations) | `PZH` (pollen stations) |
| Fetch parameter | `id` (fetch) | Should be `url` |

### Structural inconsistencies
| Aspect | Tool A | Tool B |
|--------|--------|--------|
| Timestamp | `"202604081530"` (currentWeather) | ISO 8601 (forecast) |
| No-match behavior | Error (pollen) | Silent wrong data (weather, forecast) |
| Source field | `"MeteoSwiss Open Data"` (everywhere) | Consistent ✅ |

### Behavioral inconsistencies
- "Zurich" → KLO in currentWeather, but "Zurich" → PZH in pollen. Different resolution algorithms for the same user input.
- `search` returns `"contentType": "mchweb:pages/detail-page"` but the filter parameter accepts `"content"`. The internal and external names don't match.

---

## 7. Documentation Gaps

1. **Tool description says "~160 stations"** — actual count is 158. Minor, but imprecise.
2. **No documentation of measurement fields** — An LLM doesn't know a priori that `sunshine` is in minutes per 10-min interval, or that `radiation` is global shortwave radiation.
3. **No documentation of weather icon codes** — The SVG URLs contain numeric codes (1.svg = sunny, 26.svg = high clouds). A mapping would help LLMs describe weather without fetching the SVG.
4. **Pollen description promises species** — "Shows pollen levels by type (birch, grass, etc.)" — but the response doesn't deliver this. This is false advertising.
5. **No documentation of the location resolver behavior** — Users don't know that invalid inputs will be silently geocoded to the nearest match.
6. **`generated` field in forecast not documented** — It shows when the forecast model run was produced, which is useful for freshness assessment, but an LLM won't know this without documentation.

## Recommended Priority Fixes for RC

### Must-fix before release (blockers)
1. Add species names to pollen data entries
2. Add error responses for unresolvable locations (instead of silent fallbacks)
3. Decide on meteoswissClimateData: ship or document deferral

### Should-fix before release
4. Standardize all timestamps to ISO 8601
5. Remove pollen d0/d1 duplicate measurement windows (keep only the most current)
6. Fix postal code resolution (1200 → Geneva, 3000 → Bern)
7. Fix search `pageSize` parameter (not being honored)

### Nice-to-have for future release
8. Add OBS visual observation data
9. Add wind compass direction
10. Add current weather conditions summary text
11. Rename fetch `id` parameter to `url`
12. Add pollen severity levels ("none"/"low"/"moderate"/"high"/"very high")

## What the Server Does Well

Credit where due:

1. **Fetch tool** is excellent — markdown conversion, metadata control, domain validation, clear errors.
2. **Pollen error handling** is the gold standard — lists all available stations on invalid input.
3. **Measurement structure** with explicit `{value, unit}` pairs is LLM-ideal.
4. **Coordinate distance** — Adding `distance_km` to coordinate lookups is a thoughtful touch.
5. **Search multilingual support** — All 4 Swiss national languages work with correct domain routing.
6. **Forecast weather descriptions** — "sunny", "high clouds", "overcast and dry" are natural language, not codes.
7. **Station data model** — Clean, consistent, includes elevation and municipality.
8. **Address geocoding** — "Bahnhofplatz 1 Bern" actually working is impressive.
