# GH Pages via Astro Starlight — implementation plan

**Status: awaiting Max's go-ahead.** Supersedes the generator choice in
[2026-07-11-pages-site-generator-options.md](./2026-07-11-pages-site-generator-options.md) —
Max picked Starlight directly, so this is the concrete build, not another ballot.

## What gets published

Two source trees, neither of which GH Pages' old branch-deploy could reach correctly:
1. Repo-root `docs/` — 34 markdown files (`plans/`, `sessionlogs/`, `research/`, `test-reports/`).
2. `packages/meteoswiss-forecast-evals/docs/results/` — dated markdown writeups **plus**
   promptfoo's own static HTML export (`promptfoo export eval <id> -o *.html`) — a single,
   self-contained page (own `<html>`/`<head>`, inline `<script>`, verified no external refs) that
   is promptfoo's *own* rendered UI, not markdown/JSON needing our own rendering.

Confirmed via Starlight's own docs, not assumed:
- Content pages (rendered, themed, in the sidebar) live in `src/content/docs/` and need
  `title` frontmatter — the **only required field**.
- `public/` holds files "that will not be processed by Astro" and are served byte-for-byte —
  exactly where the promptfoo HTML snapshots belong. Clicking through to one leaves Starlight's
  theme entirely and shows promptfoo's own UI — that's correct, not a bug, and worth setting
  Max's expectations on up front.

## Content sync script (the actual work)

Neither content tree already has Starlight-shaped frontmatter, and Starlight only reads from one
directory (`src/content/docs/`) — so a small prep script runs before every build:

`packages/meteoswiss-docs-site/scripts/sync-content.ts`, roughly:

1. Walk `docs/**/*.md` (repo root). **Skip symlinks** — `docs/plans/active/*` and
   `docs/plans/delivered/*` are literal symlinks back to sibling files in `docs/plans/` (verified:
   e.g. `active/prod-promotion.md -> ../2026-03-29-prod-promotion.md`); following them would
   double-list the same plan under two sidebar paths. The active/delivered curation view is a
   nice-to-have follow-up, not v1.
2. Walk `packages/meteoswiss-forecast-evals/docs/results/*.md` — same treatment, copied into
   `src/content/docs/forecast-evals/results/`.
3. For every copied `.md` file: if it has no frontmatter block, inject one — `title:` from the
   file's first `# H1` heading (both sample files checked start with a bare H1, no frontmatter),
   falling back to a title-cased filename if no H1 is found. Nothing else is required.
4. Walk `packages/meteoswiss-forecast-evals/docs/results/*.html` — copy verbatim into
   `public/forecast-evals-results/`, **no parsing, no frontmatter, not a content-collection page**.

**Linking a markdown writeup to its paired HTML snapshot:** auto-wired — the sync script matches
files by filename slug (`YYYY-MM-DD-<slug>.md` / `YYYY-MM-DD-<slug>.html`) and injects a "View the
full static run snapshot →" link right after the markdown's frontmatter when a pair exists.
Nothing to add by hand when a new dated writeup lands.

## Sidebar structure

Autogenerated per top-level folder, mirroring the existing directory layout 1:1 — no hand-curated
per-file list to maintain as new docs land:

```js
sidebar: [
  { label: 'Plans', items: [{ autogenerate: { directory: 'plans' } }] },
  { label: 'Sessionlogs', items: [{ autogenerate: { directory: 'sessionlogs' } }] },
  { label: 'Research', items: [{ autogenerate: { directory: 'research' } }] },
  { label: 'Test Reports', items: [{ autogenerate: { directory: 'test-reports' } }] },
  {
    label: 'Forecast Evals — Results',
    items: [{ autogenerate: { directory: 'forecast-evals/results' } }],
  },

```
(`autogenerate` only scans `src/content/docs/` — confirmed — so the raw HTML snapshots in
`public/` never appear as sidebar entries themselves; they're reached via the in-page links
described above.)

## Monorepo placement

Following the precedent this repo already set for `meteoswiss-forecast-evals` — a large
dev-dependency tree (there: promptfoo; here: Astro + Starlight) that shouldn't install for every
contributor on a plain root `pnpm install`:

- New package: **`packages/meteoswiss-docs-site/`**, with its **own** `pnpm-workspace.yaml` +
  lockfile, **excluded from the root workspace glob** — same pattern, same rationale, already
  proven in this repo.
- `pnpm create astro --template starlight` scaffolds the usual `astro.config.mjs`,
  `src/content.config.ts` (Starlight's frontmatter schema, boilerplate, one-time), `src/content/
  docs/`, `public/`, `package.json`.
- `package.json` scripts: `sync-content` (runs the prep script), `build` (`sync-content` then
  `astro build`), `dev` (`sync-content` then `astro dev`, for local preview).

## GH Pages base path

Verified via Astro's own deploy docs. `code.178.is` is **not** a dedicated single-repo custom
domain — it's Max's account-level Pages domain, and this site is reachable at
`code.178.is/meteoswiss-llm-tools/` (repo name in the path), so this is the **project-repo**
config shape, not the "root custom domain" shape:

```js
// astro.config.mjs
export default defineConfig({
  site: 'https://code.178.is',
  base: '/meteoswiss-llm-tools',
  integrations: [starlight({ /* ... */ })],
});
```

## GitHub Actions deploy workflow

Astro's own docs recommend `withastro/action` over hand-rolling the
`upload-pages-artifact`/`deploy-pages` steps — it wraps install + build + artifact upload in one
step, already knows the pnpm/Node-version conventions:

```yaml
name: Deploy Docs Site
on:
  push:
    branches: [main]
    paths: ['docs/**', 'packages/meteoswiss-forecast-evals/docs/results/**', 'packages/meteoswiss-docs-site/**']
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: withastro/action@v6
        with:
          path: packages/meteoswiss-docs-site
          node-version: 24
          package-manager: pnpm@latest

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: { name: github-pages, url: ${{ steps.deployment.outputs.page_url }} }
    steps:
      - uses: actions/deploy-pages@v5
        id: deployment
```

`paths:` scopes the workflow to actually-relevant changes, so an unrelated `meteoswiss-mcp` PR
doesn't trigger a docs rebuild. **Also required:** flip the repo's Pages source from "Deploy from
a branch" to "GitHub Actions" (`gh api repos/.../pages -X PUT -f build_type=workflow`, or via
Settings → Pages) — this is what actually stops the legacy Jekyll builder from running at all,
which is the second half of what's currently broken.

## Caveats / unknowns — flagging, not blocking

- **Wide tables**: the results `.md` writeups contain per-provider/per-tier pass-rate tables.
  Starlight's default theme wraps content in a fixed reading-width column; wide tables commonly
  need `overflow-x: auto` styling to avoid layout breakage. Starlight's default CSS handles basic
  table scrolling reasonably, but this should be eyeballed on the first real build rather than
  assumed fine — flagging so it's not a surprise, not because it's expected to be a real problem.
- **First-build content check**: the frontmatter-injection heuristic (first `# H1` → `title`) is
  simple and untested against all 34+ existing files — a first build should be diffed/skimmed for
  any file where the heuristic picks a bad title (e.g. a file that opens with something other than
  a clean H1) before calling this done.
- **Scope of "evals package docs"**: this plan only syncs `docs/results/` from the evals package,
  not its full `docs/` tree (`spec.md` etc., per the original ask). Trivial to extend later — one
  more line in the sync script.
